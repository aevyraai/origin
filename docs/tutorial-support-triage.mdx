title: "Tutorial: Support triage agent"
description: Diagnose a plan-act-respond pipeline that gives the wrong refund decision — and learn which span to fix and why.
---

This tutorial walks through diagnosing a real failure in a customer-support
triage agent. The agent is given a duplicate-charge complaint and incorrectly
denies the refund. You'll see:

- how Origin identifies the culprit span
- how `fix_type` tells you the failure is in the **prompt** (not the retriever)
- how the prompt-level rollup feeds directly into Reflex

The full code is in
[`examples/support_triage/`](https://github.com/aevyraai/origin/tree/main/examples/support_triage)
in the origin repo.

## The pipeline

The triage agent is a plan-act-respond loop:

```
plan (round 1)   → planner decides which tools to call
  ├── stripe_lookup   → pull the user's recent charges
  ├── kb_search       → fetch the refund policy
  └── thread_search   → prior support threads
plan (round 2)   → planner reads tool results and decides eligibility
respond          → responder drafts the user-facing reply
```

Both `plan` spans share `prompt_id="planner"` — they represent two firings
of the same planner prompt. The `respond` span has its own
`prompt_id="responder"`.

```python
from aevyra_witness.runtime import span, trace
from aevyra_witness import KIND_REASON, KIND_TOOL

@span("stripe_lookup", kind=KIND_TOOL)
def stripe_lookup(customer_id): ...   # returns two identical charges

@span("kb_search", kind=KIND_TOOL)
def kb_search(query): ...             # returns the refund policy doc

@span("thread_search", kind=KIND_TOOL)
def thread_search(customer_id): ...   # returns no prior complaints

def triage_agent(user_message):
    with span("plan", kind=KIND_REASON, prompt_id="planner", optimize=True) as p1:
        ...  # round 1: dispatch tools

    with span("plan", kind=KIND_REASON, prompt_id="planner", optimize=True) as p2:
        ...  # round 2: decide eligibility  ← THIS IS WHERE THE BUG IS

    with span("respond", kind=KIND_REASON, prompt_id="responder") as r:
        ...  # draft the reply
```

## The bug

The `kb_search` tool returns the correct refund policy:

> *"Duplicate charges posted within 24 hours of one another are automatically
> eligible for a refund."*

The `stripe_lookup` tool returns two identical `$29.00` charges on the same
day. The evidence is unambiguous.

Despite this, the planner (round 2) confabulates an explanation:

> *"One charge is the monthly Pro subscription renewal; the other is a
> prorated upgrade charge posted on the same day."*

It decides `eligible_for_refund: False`. The responder dutifully tells the
user no refund is needed. The answer is wrong.

## Running the diagnosis

```python
from aevyra_origin import diagnose_pipeline
from aevyra_origin.llm import anthropic_llm

result = diagnose_pipeline(
    triage_agent,
    "I was charged $29 twice on the same day — can you issue a refund?",
    judge=judge,
    rubric=(
        "Acknowledge the duplicate charge, cite the refund policy, and "
        "confirm the refund is being issued. Refusing or reframing the "
        "charges must score low."
    ),
    llm=anthropic_llm(),
    runner=runner,    # enables causal ablation
    method="all",
)

print(result.render())
```

The judge scores the trace at **0.2** — the agent refused a clearly valid
refund.

## What Origin finds

```
Origin attribution  (method=all, score=0.200)
  Summary: The planner (round 2) misread the tool evidence and incorrectly
  concluded the charges were distinct line items rather than a duplicate.
  The refund policy was retrieved correctly; the failure is in how the
  planner interpreted the data.

  1. plan (id=p2)  [primary, confidence=0.91, fix=prompt]
     Round-2 planner confabulated an upgrade charge that does not appear
     in the stripe_lookup results, overriding clear evidence of a
     duplicate and reaching an incorrect eligibility decision.

  2. respond (id=r1)  [minor, confidence=0.21, fix=prompt]
     The responder faithfully executed the planner's wrong decision.
     Fixing the planner will fix this span as a side effect.

  --- Prompt-level rollup (for Reflex) ---
  prompt=planner    [primary, confidence=0.91, spans=2]
  prompt=responder  [minor, confidence=0.21, spans=1]
```

Both culprits have `fix_type="prompt"`. The retrieval worked — `kb_search`
returned exactly the right policy. The problem is that the planner prompt
doesn't anchor the LLM firmly enough to the tool results it receives: the
model ignored the evidence and invented a narrative instead.

This is something Reflex can fix.

## What it means for each fix_type

This scenario landed entirely on `fix=prompt`. But the same pipeline could
surface different failure types depending on what went wrong:

| Scenario | Culprit | fix_type |
|---|---|---|
| kb_search returns the wrong doc | `kb_search` | `retrieval` |
| stripe_lookup sent wrong customer_id | `stripe_lookup` | `tool_schema` |
| Planner ignores evidence | `plan` | `prompt` |
| stripe_lookup timed out | `stripe_lookup` | `infrastructure` |
| Pipeline called wrong tool entirely | routing logic | `routing` |

When Origin returns `fix=retrieval`, you fix the index. When it returns
`fix=prompt`, you hand the result to Reflex. Origin tells you which is which
so you don't spend time on the wrong lever.

## The prompt-level rollup for Reflex

`result.by_prompt()` aggregates span-level blame up to the prompt level —
useful when the same prompt fires at multiple steps:

```python
for pa in result.by_prompt():
    print(f"prompt={pa.prompt_id}  severity={pa.severity}  confidence={pa.confidence:.2f}")
    print(f"  spans: {[s.node_id for s in pa.spans]}")
    print(f"  reasoning: {pa.reasoning[:120]}...")
```

```
prompt=planner    severity=primary  confidence=0.91
  spans: ['p1', 'p2']
  reasoning: [p2] Round-2 planner confabulated an upgrade charge...
prompt=responder  severity=minor    confidence=0.21
  spans: ['r1']
  reasoning: [r1] The responder faithfully executed the planner's wrong decision...
```

Both plan spans (`p1`, `p2`) share `prompt_id="planner"`. Reflex updates that
prompt once and every call site benefits.

## Adding causal ablation

The runner replays the pipeline with one span's output replaced by a neutral
placeholder. A large score drop confirms the span is genuinely causal:

```python
from aevyra_witness import AgentTrace, TraceNode

def runner(original: AgentTrace, overrides: dict) -> AgentTrace:
    new_nodes = [
        TraceNode(
            name=n.name, input=n.input,
            output=overrides[n.id] if n.id in overrides else n.output,
            id=n.id, parent_id=n.parent_id, kind=n.kind,
            optimize=n.optimize, prompt_id=n.prompt_id,
            metadata=dict(n.metadata),
        )
        for n in original.nodes
    ]
    return AgentTrace(nodes=new_nodes, ideal=original.ideal, metadata=dict(original.metadata))
```

Pass `runner=runner` to `diagnose_pipeline` and it runs ablation alongside
the LLM methods. Ablating `p2` (the round-2 planner) causes the score to
drop to near 0, confirming it as the primary cause — not just a suspicion.

## Running the example

```bash
cd examples/support_triage
export ANTHROPIC_API_KEY=sk-ant-...
python diagnose.py
```

The pipeline stubs are deterministic — no LLM tokens are burned by the
pipeline itself. Only the attribution LLM call costs tokens.
